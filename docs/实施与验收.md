# 实施与验收

- 状态：第四版计划组成部分，已批准，实施中
- 上级入口：`docs/开发计划.md`
- 唯一职责：阶段执行、Git 门禁、自动化、集成、发布、测试环境清理和完成标准

## 1. 每阶段 Git 纪律

阶段开始前：

1. `gh auth status` 必须显示活动账号为 `SeireiA`。
2. `origin` 必须是 `https://github.com/SeireiA/dsh-plugin-rtk.git`。
3. 当前分支必须是 `main`，工作树必须干净。
4. 本地 HEAD 必须与 `origin/main` 一致。
5. Git author 使用 `SeireiA` 和该账号的 verified/noreply email。
6. 读取上一阶段验证记录和本阶段 Owner 文档，防止计划漂移。

阶段结束时：

1. 完成本阶段全部自动化和人工验证。
2. 执行工程规模、复杂度、依赖图和覆盖率门禁。
3. 精确暂存本阶段文件，不混入下一阶段内容。
4. 使用详细中文主题和正文提交，正文列出行为、验证和边界。
5. 由当前活动账号 `SeireiA` 推送 `origin/main`。
6. 比较本地 HEAD 与远端 `refs/heads/main`，SHA 必须一致。
7. 记录阶段 SHA；失败时停止，不进入下一阶段。
8. 禁止 force push 或改写已推送阶段历史。

## 14. 阶段 9：测试环境清理

### 14.1 清理前基线

最终集成测试开始前创建只读基线清单，记录：

- `web` Profile 的 package list、`package.json`、lockfile 和 `cordis.patch.yml` hash。
- 同名 package 是否存在；若存在，记录精确版本、resolution、integrity 和来源路径。
- `dsh --profile web --dump-config` 输出 hash。
- 插件 runtime 根是否预先存在；若存在，记录完整路径清单和 hash，不声明任务所有权。
- 本次验收生成的随机 `acceptanceRunId`、待安装 tarball SHA-256 和开始时间。
- 测试 Profile、mock server 端口、后台 job 和浏览器存储 key。
- 仓库 HEAD、`origin/main` SHA 和工作树状态。

只有同名 package 和 runtime 根在基线中都不存在，才允许把 `web` Profile 用作最终测试安装。安装后由验收 harness 在 runtime 根写入仅用于清理归属证明的 marker，包含 acceptanceRunId、tarball hash 和测试窗口；测试结束立即生成路径、大小、mtime 和 hash 清单。

若 package/runtime 在测试前存在、marker 不匹配、当前 package 不再解析到本次 tarball、测试结束清单后出现新写入或目录混合未知文件，都视为可能的用户状态：禁止卸载或删除，停止阶段 9并请求用户确认精确范围。

### 14.2 清理目标分类

- `derived/test-state`：任务创建的测试 Profile、mock Release server、临时 HOME、fixture DB、coverage、Playwright 输出、dist、临时 tarball和下载目录。验证归属后删除。
- `test-created persistent-state`：最终 GUI 验收创建的插件专属 runtime data。基线证明测试前不存在时，按用户当前要求删除。
- `user/pre-existing state`：DSH Session、其他插件、全局 RTK、预先存在的同名目录和用户 Profile 修改。禁止删除或覆盖。
- `release/source-of-truth`：Git 仓库、GitHub Release、tag、源代码、lockfile和已推送历史。必须保留。

### 14.3 清理顺序

1. 停止本任务启动的 dev watcher、fixture server、Playwright browser 和所有后台 job，并结束测试写入窗口。
2. 执行清理 guard：基线 package/runtime 均不存在、当前 package 精确解析到本次 tarball、ownership marker 匹配 acceptanceRunId/tarball hash、runtime 与测试结束清单无后续写入或未知文件。任一条件失败立即停止，不执行后续删除。
3. guard 通过后才在 `web` Profile 执行 `dsh plugin --profile web remove dsh-plugin-rtk`，由 pnpm 移除本次测试依赖。
4. 比较 Profile 与基线，只恢复 RTK 测试产生的 composition/package delta；检测到同期用户修改时保留该修改并停止自动恢复。
5. 若创建了独立测试 Profile，确认目录 marker、package resolution 和 acceptanceRunId 都属于本任务后再删除。
6. 再次确认插件进程已卸载且 runtime marker 未变化，然后只删除 marker 清单列出的 `$DSH_HOME/plugins/dsh-plugin-rtk` runtime、候选、测试 data segments、catalog cache 和测试报告；禁止通配删除父目录中的其他内容。
7. 清除浏览器中仅属于 `dsh-plugin-rtk` 的 local/session storage key；不清除 DSH 其他站点数据。
8. 删除仓库内由本任务创建的 ignored 派生产物：`node_modules`、`dist`、`lib`、`coverage`、`playwright-report`、`test-results`、临时截图和本地 `.tgz`。
9. 清理 OS temp 下带本次 acceptanceRunId 的目录、lock 和未完成下载。
10. 刷新现有 Web GUI，确认 RTK overlay 消失，原 shell executor 恢复。
11. 清理后不得再次安装或运行插件集成测试；后续只做只读验证。

### 14.4 清理验证

1. `dsh plugin --profile web list --depth=0` 不包含 `dsh-plugin-rtk`。
2. `dsh --profile web --dump-config` 不包含 RTK plugin row，原 shell executor 与基线一致。
3. 插件测试 runtime、测试 Profile、临时目录和派生产物不存在。
4. 任务创建的后台进程和端口均已释放。
5. 浏览器刷新后无悬浮球、无 RTK Client contribution、无 console error。
6. 用户 Session、其他插件和全局 RTK 状态与基线保持。
7. 仓库工作树干净，HEAD 等于 `origin/main`；GitHub Release/tag/checksum 保持可用。
8. 输出清理清单，逐项标记 removed、restored、preserved 或 skipped-with-reason。

清理 guard 因可能的用户状态停止时，整体状态是 `needs-confirmation`，不能宣称已清场，也不能进入手动初版安装交接。

## 15. 风险与处理

| 风险                  | 处理                                              |
| --------------------- | ------------------------------------------------- |
| prerelease 行为不稳定 | 显式标签、二次确认、完整测试、旧版本持续服务      |
| 历史 Release 不兼容   | 仍列出，但由资产/checksum/兼容性结果阻止激活      |
| tag 不是 semver       | 使用 release id 与 published_at，不以 semver 过滤 |
| 目录过大              | Host cursor、每页 30、ETag、去重和 revision       |
| 新版迁移旧 DB         | 每 Release 独立 segment，只由同 binary 读取       |
| 更新中断 shell        | side-by-side，ready 前继续旧描述符                |
| 共享 Owner 增长       | 400 行硬门禁和依赖边界，按职责拆分                |
| 过度拆分产生耦合      | public port、最多 8 个内部依赖、无深路径导入      |
| 清理误删用户状态      | 测试前基线、归属证明、用户状态禁止删除            |
| 清理后又污染环境      | 清理后只读验证，不再安装或运行集成测试            |

## 16. 完成标准

只有同时满足以下条件才完成：

1. 公开、非 fork 仓库与 `dsh-plugin` Topic 正确。
2. 每阶段有验证、中文提交、SeireiA 推送和匹配远端 SHA。
3. 所有手工文件不超过 400 行，复杂度、依赖图、重复率和未使用检查通过。
