## 1. 修订原因

第五版使用 `shellEnv + typed guidance` 鼓励 Agent 显式调用 wrapper，但不能保证适用命令实际经过 RTK。用户把“提高主动使用概率”提升为强制要求：active pointer 存在时，每个受覆盖的 DSH Bash/Pwsh ToolExecution 都必须先由该 Runtime 的官方 `rtk rewrite` 判定，RTK 判定适用的原命令不得直接执行。

Context7 与目标版本公开资料共同确认：

1. DSH rc.7/rc.1 的 `tools/pre-execute` 只允许 `allow`、`deny` 或 `ask`；输入已记录和展示，因此排除 `updatedInput` 与参数改写。
2. `ShellExecutor.resolve()` 只补默认值和限制上限；`tools/execute` around-dispatch 也不能改变调用 identity。
3. RTK 官方 Hook 以每命令一次的 `rtk rewrite` 作为适用性唯一真相；支持 `updatedInput` 的 Agent 可透明改写。
4. RTK 对不支持 `updatedInput` 的 GitHub Copilot CLI 采用官方 `deny-with-suggestion`：阻止原调用并要求 Agent 以 RTK 命令重试。
5. 用户已选择活动期严格失败语义：active Runtime 存在时，`rewrite` 超时、异常或输出不可判定均拒绝该 Bash/Pwsh 调用；无 active Runtime 时原 shell 保持可用。
6. rc.7/rc.1 目标源码确认内置 tool identity 都是 `bash`、`pwsh`，必填 command 路径都是 `exec.arguments.command:string`，并公开了 DSH-issued `exec.token` 与 terminal monotonic `ctx.tools.guard()`。
7. 两版本 scheduler 顺序同为 pre-execute waterfall → 必要时 approval → guards → dispatch；waterfall `next()` 只进入下一 listener，不能提前执行 body。
8. RTK `v0.44.2`/`v0.45.0` 目标源码确认 `rewrite` exit `0/1/2/3` 分别为 allow rewrite、passthrough、deny、ask rewrite；因此“全部非零即故障”不是有效契约。
9. 第五版确认的 standalone Typert/Client builder 缺口仍存在，但它与 Host 命令判定能力是两个独立 gate。

第六版候选采用 DSH 官方 deny/ask decision 和 RTK 官方 rewrite classification owner，不恢复第四版 executor replacement、假 workspace、参数 mutation 或私有 workaround。

## 2. 首版目标

开发一个长期安装到 DSH Profile 的 Cordis Host/Client 插件，安全管理官方 RTK 二进制，通过 DSH 原有 Bash/Pwsh 工具直接调用 RTK，并在 Web GUI 展示统计和 Release 管理界面。

首版可观察结果：

1. 最低兼容 DSH `0.1.0-rc.7`，并验证已发布的 `0.1.1-rc.1`。
2. `Stage 1H` 先证明 rc.7/rc.1 的官方 Host bundle、Cordis lifecycle、`shellEnv`、`agent/session-start`、异步 `tools/pre-execute` classifier 与同步 `ctx.tools.guard()` receipt gate；失败则停止 Host 与业务核心。
3. `Stage 1C` 独立证明 Client、Remote、Client loader 和 `shell.overlay`；第五版失败事实继续阻断阶段 6 至阶段 9 与正式发布，但不再阻断已通过 1H 的阶段 2 至阶段 5。
4. Windows、macOS 和 Linux 使用官方 Release 的当前平台预编译资产。
5. 下载必须有可信 SHA-256：优先核对 GitHub asset digest，存在 `checksums.txt` 时交叉验证。
6. 通过 DSH `shellEnv` 只贡献插件拥有的 `DSH_RTK_*` 变量，不修改 PATH、shell profile 或全局 RTK。
7. 有 active Runtime 时，每个受覆盖 ToolExecution 先以无 shell subprocess 交给该版本 binary 的 `rewrite`；插件不维护命令白名单。
8. Classifier 生成 execution-token receipt，同步 monotonic guard 拒绝缺 receipt 的受覆盖调用；适用原调用只返回稳定重试指令，Agent 重试仍完整进入 DSH 原判权和 sandbox。
9. active Runtime 下 `rewrite` 超时、协议错误或生命周期中止均严格拒绝；无 active Runtime 时 gate 不宣称强制能力，原 shell 完全可用。
10. wrapper 只设置版本 binary、`RTK_DB_PATH` 和 `RTK_TELEMETRY_DISABLED=1`，再调用官方 RTK CLI。
11. startup、clear、compact 和必要的 resume 注入 `kind:rtk-guidance`、`version:3` 的短指导，优先减少首次 deny/retry。
12. 首次安装基线为官方 RTK `v0.45.0`。
13. Release 目录展示官方仓库全部 `draft:false` Release，包括 stable、prerelease 和历史版本。
14. 所有公开 Release 都可查看、选择并可尝试候选下载；只有具备本平台官方资产、可信校验值、可绑定的 tagged/CLI rewrite contract evidence 且真实 binary matrix 通过的候选才能激活。
15. 插件保证 RTK `v0.44.2` 及以后版本兼容；更旧版本只做尽力兼容。旧版有 contract 证据并通过同一矩阵时仍可激活；证据不足或版本不可解析时只能保留为 inactive inspection。
16. Token 数据跨实际安装且数据可读的 Release 聚合；每段由对应 RTK binary 读取自己的版本化 `RTK_DB_PATH`。
17. Web GUI 最终提供悬浮球、“总览、今日、当前仓库”三个标签页和全 Release 选择器，并显示强制判定状态。
18. 每个阶段独立验证、中文提交、推送并核对本地与 `origin/main` SHA。
19. Host-first 只允许隔离 Profile 预览和验收；完整 Client/Remote/GUI 通过前不得创建正式 npm/GitHub Release。
20. 全部测试和 GitHub Release 完成后，只清理本任务可证明拥有的安装、数据、进程和派生产物，并保持插件未安装。

### 2.1 强制判定规范

唯一规范如下，其他文档只展开实现与验收：

| DSH 版本 | 受覆盖 Tool identity | 必须存在的参数                   |
| -------- | -------------------- | -------------------------------- |
| rc.7     | `bash`、`pwsh`       | `exec.arguments.command: string` |
| rc.1     | `bash`、`pwsh`       | `exec.arguments.command: string` |

1. 保证边界是通过目标版本完整枚举出的官方 `bash`/`pwsh` ToolExecution，包括同 identity 的 persistent 实现；脚本内部子进程、其他 Tool、交互终端和插件自有 subprocess 不在本 gate 覆盖范围。
2. 保证以 guard decision 为边界：active pointer 只在候选 contract 全部通过后 commit，存在即 `enforcing`；此前已通过 inactive guard 的调用不追溯拦截，尚未过 guard 的 inactive-start 调用在 activation 后拒绝。
3. Enforcing 时，每个受覆盖调用都必须取得由 DSH `exec.token` 绑定的 one-shot receipt；缺少/非对象 arguments、缺少 command、command 非 string、listener 被跳过、receipt 过期或 Runtime generation/contract 漂移均严格拒绝。
4. 有效 command 以单个 argv 交给 active binary 的 `rewrite`。Exit `0` different 表示适用并 deny，`0` same 表示 converged 并 allow；exit `1` empty 表示 no-match 并 allow；exit `2` empty 表示 policy deny；exit `3` different 表示 ask rewrite 并 deny，`3` same 必须返回 DSH `ask`，不能因文本相同降成 allow。
5. 每个 candidate 还必须证明合法行的 stderr policy；除穷尽矩阵外，超时、取消、其他 exit、无效 UTF-8、NUL、输出越界、协议不一致或 receipt 缺失全部拒绝。任何 candidate 无法提供 tagged/CLI contract evidence 并通过 binary matrix 都不得 enforcing，best-effort 不降低该不变式。
6. Gate 不自动重试、不执行 RTK 输出、不修改原参数。Denial 只提供稳定 code 和 Bash/Pwsh wrapper 模板；Agent 提交新的 ToolExecution，最终调用重新判定并重新经过 DSH approval/sandbox。
7. Enforcing guard decision 下，每个受覆盖 ToolExecution 都是“valid command 被 verified active RTK 分类”或“在 dispatch 前拒绝”；no-match 可原样执行，适用原调用不得 dispatch。该限定是“所有适用命令必经 RTK”的唯一完成口径，不承诺 RTK 分类本身无缺陷或任意 retry 都成功。

## 3. 明确不实现

1. 不替换或继承 DSH 内置 Bash/Pwsh executor，不注册第二个 shell Tool。
2. 不在 `tools/pre-execute`、`tools/execute` 或 `ShellExecutor.resolve()` 中改写工具参数；policy adapter 只返回官方 `allow`/`deny`/`ask` decision。
3. 不复制 RTK rewrite registry、维护命令白名单或自行解析 shell 语义；verified active binary 拥有 classification 语义，DSH gate 拥有“已分类或拒绝”的路由保证，插件不独立证明 RTK 映射正确。
4. 不把 deny gate 变成命令审计库，不持久化原命令、改写建议或“未命中语句”，不增加第四个标签页。
5. 不自制 Typert generator wrapper、假 workspace、协议源码镜像或手写 generated codec。
6. 不修改、patch、vendor 或运行时 monkeypatch DSH/RTK 源码。
7. 不依赖 DSH 或 RTK 未导出的内部路径、反射结果和私有对象结构。
8. 不执行 `rtk init`，不安装全局 Hook，不修改用户 PATH、shell rc、PowerShell Profile 或全局配置。
9. 不直接读写或迁移 RTK SQLite。
10. 不把 GitHub 上可浏览但从未安装的 Release 计入 Token 统计。
11. 不保证 RTK `v0.44.2` 之前版本可用，也不为其增加专用兼容分支。
12. Client/Remote 闭环失败时可以交付隔离 Host 预览证据，但不得发布 Host-only 正式版本或把项目标记为完成。

## 5. 兼容性口径

### 5.1 DSH

1. 最低支持 `0.1.0-rc.7`。
2. `0.1.1-rc.1` 是 npm 已发布的最高版本；2026-08-21 续行复核时 `latest` 与 `next` 均指向该版本，必须继续进入兼容矩阵。
3. Stage 1H 在 rc.7 和 rc.1 分别验证 Host install/lifecycle、`shellEnv`、typed guidance、完整 `bash`/`pwsh` schema、async classifier 和 monotonic guard。
4. Stage 1C 在两个版本分别验证官方 Client/Remote/loader/Slot；现有失败保持为阶段 6 至阶段 9 的 blocker。
5. 任一版本差异必须通过公开 API 处理；禁止维护按内部结构探测的兼容层。
6. rc.7 无法完成 1H 时停止 Host 与核心开发；无法完成 1C 时不抬高最低版本、不发布正式插件，但不否定已独立通过的 Host/core 证据。

### 5.2 RTK

1. GitHub tag 仍作为不透明目录 identity；目录排序使用 `published_at` 和 release id。
2. 兼容保证以候选 binary 报告的语义版本为准：`>=0.44.2` 属于保证范围。
3. 无法报告标准语义版本或 `<0.44.2` 的候选属于尽力兼容范围。
4. 两类候选都必须经过相同资产、checksum/digest、安全解压、直接调用、gain 和 rewrite gate 测试；fixture 测试不能替代 tagged/CLI contract evidence。
5. Rewrite gate 测试至少覆盖候选 exit 0/1/2/3 与 stdout/stderr matrix、same-output、schema/receipt/generation、Agent retry、超时、协议漂移、输出越界和取消。
6. 保证范围测试失败属于插件缺陷并阻断阶段；尽力兼容版本缺证据或测试失败只允许 inactive inspection，不扩大专用适配。
7. 所有 `draft:false` Release 始终可见、可选和可查看失败原因。

## 6. 已确认官方事实

1. DSH 插件包通过 `dsh.bundle` 指向 patch，并通过 `dsh plugin --profile <name> add <package>` 安装。
2. DSH `shellEnv` 允许插件注册 fiber-owned `DSH_*` 环境变量。
3. DSH rc.7/rc.1 的工具参数在 pre-policy 前已经记录和展示；`PreToolDecision` 只有 `allow`、`deny`、`ask`，官方契约明确排除输入改写。
4. 两个目标版本的内置 Tool 都使用 `bash`/`pwsh` 与 `arguments.command:string`，`exec.token` 是 registry-issued unique symbol。
5. 两版本 scheduler 都先 await 完整 pre-execute waterfall，再处理 ask approval，然后执行只能 deny 的 guards，最后才 dispatch；listener `next()` 不会越过该顺序。
6. `tools/execute` around-dispatch 可以做 timeout、retry 或 metrics，但 call identity 不可变。
7. RTK 官方 Hook 每次命令启动一个新 `rtk rewrite` 进程，rewrite registry 是 classification 语义真相。
8. RTK 对没有 `updatedInput` 的 Copilot CLI 使用 `deny-with-suggestion`；这为 DSH 的不可变参数契约提供官方同类实现依据。
9. RTK v0.44.2/v0.45.0 `rewrite` 的 exit 0/1/2/3 分别表示 allow rewrite、passthrough、deny 和 ask rewrite；每个候选仍须实测。
10. RTK 官方 Hook 默认故障放行；第六版的 active Runtime 严格阻断是用户明确选择的更强项目策略，必须单独测试。
11. RTK 官方文档支持直接以 `rtk <tool> <args>` 形式执行命令，未识别命令可使用 proxy/pass-through 语义。
12. RTK `gain --all --format json` 是机器可读统计来源；`RTK_TELEMETRY_DISABLED=1` 是官方禁用遥测方式。
13. RTK `v0.45.0` 为公开 stable，并提供目标平台资产、`checksums.txt` 和 GitHub SHA-256 digest。

## 8. 第六版候选决策

1. 有 active Runtime 时，目标版本枚举出的官方 `bash`/`pwsh` ToolExecution 必须取得 RTK classification receipt；适用原命令不得直接执行。
2. DSH 不支持 `updatedInput`，因此借鉴官方 deny-with-suggestion 交互，但本插件只返回无命令文本的 wrapper retry instruction，不改写或自动执行 RTK suggestion。
3. Active Runtime 下 schema、receipt、rewrite contract 或 lifecycle 检查失败严格拒绝；无 active Runtime 时原 shell 可用且不宣称强制保证。
4. Async classifier 与 monotonic guard 共同闭合 listener short-circuit；RTK binary 仍是 applicability 唯一 Owner。
5. Guidance v3 负责减少首次原命令尝试，command gate 负责最终执行不变式，两者不互为 fallback。
6. 首版 UI 仍为“总览、今日、当前仓库”三个标签页，只显示 `inactive`/`enforcing` mode，不持久化 per-call blocked。
7. 所有公开 Release 可见、可选、可尝试下载安装；保证 `v0.44.2` 及以后，之前版本尽力兼容，但只有 tagged/CLI contract evidence 与真实 binary matrix 都成立才可激活。
8. 统计跨实际安装且数据可读的历史 Release 聚合；不持久化 shell 命令或实现“未命中语句”。
9. 最低兼容 DSH rc.7，同时验证 rc.1；1H 通过后允许 Host/core 预览，1C 未通过前不得正式发布。
10. 不制作 Typert workaround、executor replacement、全局 Hook、shell parser 或插件命令白名单。

2. `@deepseek-ai/dsh-typert-generator` rc.7/rc.1 都公开 analyzer/emitter/generator 与 `./tsdown` API，但没有 CLI 或文档化 standalone build integration。
3. 两个版本的公开 tsdown plugin 在本仓库这种 workspace 根 package 拓扑下均完成调用但生成 0 个 Typert artifact。
4. Tagged source 和 tests 解释该结果：现有发现过程只处理 aggregate project references 下 `<root>/packages/**` 的 contributor；该实现细节只作诊断，不作为公共契约。
5. 直接编排 analyzer/emitter、迁移成 DSH 风格假 workspace 或维护 generator wrapper 都命中第五版禁止项。
6. Client loader 能消费预构建 `dsh.client`/`./client`，但在 rc.7/rc.1 公开 exports、官方文档和已执行检索中均未发现文档化、可导出的第三方 lazy-CJS Client bundle builder。

8. 用户于 2026-08-22 明确批准重新设计命令采用边界，并选择 active Runtime 下 rewrite 检查失败严格阻断。
9. 第六版候选将原 Stage 1 拆为 1H 与 1C；历史 Typert/Client 失败只归入 1C。候选文档整体获批并提交前，不启动 1H 或业务代码。
10. 1H 通过后才允许阶段 2 至阶段 5；1C 仍须等待上游官方 standalone Typert/Client build 路径或再次批准调整禁止边界，且在通过前继续阻断阶段 6 至阶段 9 和正式发布。

## 10. 第六版候选审批门禁
