# 架构与运行时

- 状态：第四版计划组成部分，已批准，实施中
- 上级入口：`docs/开发计划.md`
- 唯一职责：Host/Client 边界、Release 运行时、RTK 测试门禁、命令接管与诊断

## 1. 总体结构

```text
DSH Profile composition
  |
  +-- Host: RtkRuntimeService
  |     +-- 活动版本描述符与版本化 RTK_DB_PATH
  |     +-- 初始安装、运行状态和多版本 gain 聚合
  |
  +-- Host: RtkReleaseCatalog
  |     +-- 全部公开 GitHub Release 分页目录
  |     +-- stable/prerelease/历史版本与平台能力投影
  |
  +-- Host: RtkUpdateService
  |     +-- 候选下载、checksum、安全解压
  |     +-- 强制兼容性测试、原子激活和回滚
  |
  +-- Host: RtkGuidancePlugin
  |     +-- agent/session-start 生命周期注入
  |
  +-- Host: RtkRewriteClassifier
  |     +-- 活动版本 rtk rewrite 同步分类
  |
  +-- Host: RtkDiagnosticsService
  |     +-- 带 RTK 版本的命中/未命中聚合
  |
  +-- Host: RtkSandboxBashExecutor / RtkSandboxPwshExecutor
  |     +-- 保留 DSH sandbox executor 语义
  |
  +-- Host: rtkDashboard Typert Remote
  |     +-- 统计、Release 目录、更新操作和状态
  |
  +-- Client: RtkOverlay
        +-- shell.overlay 悬浮球、四标签页和 Release 选择器
```

## 2. 标准 DSH 边界

1. 生命周期和依赖注入使用 `@deepseek-ai/cordis`。
2. Bash/Pwsh 接管使用 DSH `ctx.shell` executor seam；适配器调用 `super.resolve()` 保留 workdir、timeout、env、sandbox、退出码和后台任务事实。
3. RTK 实际命令、gain、版本探测和兼容性测试使用 `ctx.subprocess`。
4. `ShellExecutor.resolve()` 与后台 `start()` 是同步边界，rewrite 分类必须在命令启动前同步完成。
5. DSH `ctx.web.fetch` 只能返回解码后的 `html/text`，不能传输二进制资产；Release 元数据、checksum 和资产流由 Host `node:https` 流式客户端获取。
6. 所有 HTTPS request、response stream、临时文件和测试进程由 `ctx.effect()` 持有，并绑定 `AbortSignal`。
7. Host/Client 使用 `@deepseek-ai/dsh-typert-protocol` 的 strict Remote 与生成 codec，不传 live Service、Context、Error 或路径对象。
8. 指导使用 `agent/session-start` 与 `agent.inject()`，不修改系统提示词或工作区 `AGENTS.md`。
9. 诊断和运行状态索引使用 `ctx.storageDomain`；RTK Token 历史只由版本化 `RTK_DB_PATH` 管理。
10. Client 在 `shell.overlay` 注册 `rtk-token-overlay`，使用 `useSessions` 的 `current` 和 `byId[current].cwd`，不推断产品 DOM。
11. timer、Slot、Remote contribution、observable 和订阅全部归属当前 Cordis fiber，卸载时自动释放。
12. Profile 使用插件自带 `cordis.patch.yml` 按平台替换对应 shell executor。

## 3. 所有权与依赖方向

| 能力                   | 唯一 Owner                   | 禁止事项                      |
| ---------------------- | ---------------------------- | ----------------------------- |
| 活动版本描述符         | `RtkRuntimeService`          | UI、executor 不维护旁路指针   |
| Release 列表与平台能力 | `RtkReleaseCatalog`          | Update Service 不重复分页逻辑 |
| 下载、测试和切换       | `RtkUpdateService`           | Runtime 不自行选择候选        |
| rewrite 判定           | 活动 RTK `rewrite`           | 插件不维护命令白名单          |
| 指导注入               | `RtkGuidancePlugin`          | 不混入 executor 或 UI         |
| 未命中诊断             | `RtkDiagnosticsService`      | 不保存输出或环境对象          |
| 单版本 Token 真相      | 同版本 RTK `gain` JSON       | 不直接读 SQLite               |
| 跨版本汇总             | `RtkRuntimeService`          | Client 不自行求和             |
| 仓库范围               | Host repository scope helper | Client 不向上扫描文件系统     |
| 页面数据与操作         | `rtkDashboard` Remote        | 不暴露 Host 内部对象          |
| 悬浮交互状态           | `RtkOverlay`                 | 不写入 Host 持久状态          |

依赖只允许指向更稳定层：schema/types -> pure domain helper -> runtime service -> adapter/Remote -> Client projection。Host 不导入 Client；Client 不导入 Host 实现；Update Service 通过 Runtime port 发布已验证描述符，不访问 executor 内部。

## 4. 会话与压缩指导

监听 `agent/session-start`：

| source    | 行为                           |
| --------- | ------------------------------ |
| `startup` | 新会话首次注入                 |
| `clear`   | 清空后的新上下文注入           |
| `compact` | 每次压缩完成后重新注入         |
| `resume`  | 缺少同版本 typed source 时补入 |

typed source 使用 `kind: rtk-guidance` 与 `version: 1`。每个生命周期最多注入一次，不按文案字符串猜测。

固定模型可见文案：

```text
RTK 已挂载：在语义等价时，尽量使用 RTK 支持的单条 shell 命令，以减少命令输出 Token。不要为了使用 RTK 改变命令语义、拆分必须原子执行的操作或绕过 DSH 权限；插件会自动调用 rtk rewrite，未命中时原样执行。
```

注入失败只记录 Host 警告，不阻断 Session；平台明确不支持时不注入误导提示。

## 5. Release 目录

### 5.1 数据源与分页

1. 使用 GitHub `GET /repos/rtk-ai/rtk/releases?per_page=100&page=N`，不能使用只返回稳定版的 `releases/latest` 作为目录真相。
2. 持续请求到空页或不足 100 项；每页使用 ETag/`If-None-Match`，目录 ready 后每 24 小时最多后台刷新一次。
3. 只排除 `draft: true`；公开 stable、`prerelease: true` 和历史 Release 全部保留。
4. Release identity 使用 GitHub `id`、`tag_name`、`published_at` 和资产 id；tag 按不透明字符串处理，不用 semver 过滤。
5. 列表按 `published_at` 倒序，release id 作为稳定次序；Host 提供 cursor 分页，Client 不一次接收全部目录。
6. 手动“检查 Release”绕过目录时间缓存，但仍复用 ETag。
7. 防御 GitHub 分页重复或中途变更：按 release id 去重，并在 cursor 中带 catalog revision。

### 5.2 平台资产识别

当前平台按有序别名匹配官方资产：

| 平台        | 有序资产名                                                                               |
| ----------- | ---------------------------------------------------------------------------------------- |
| Windows x64 | `rtk-x86_64-pc-windows-msvc.zip`                                                         |
| macOS x64   | `rtk-x86_64-apple-darwin.tar.gz`                                                         |
| macOS arm64 | `rtk-aarch64-apple-darwin.tar.gz`                                                        |
| Linux x64   | `rtk-x86_64-unknown-linux-musl.tar.gz`，再尝试历史 `rtk-x86_64-unknown-linux-gnu.tar.gz` |
| Linux arm64 | `rtk-aarch64-unknown-linux-gnu.tar.gz`                                                   |

校验来源和解析规则：

1. 同一 Release 中 `checksums.txt` 必须恰好一个；重复 checksum 资产直接判为目录异常。
2. checksum 资产必须来自 GitHub API 返回的官方 asset URL，大小不超过 1 MiB，HTTP 2xx、未截断且能严格解码为 UTF-8。
3. 只接受 64 个十六进制字符的 SHA-256，以及 `<hex><空白><filename>` 或 `<hex><空白>*<filename>` 两种常见行格式。
4. filename 必须是目标资产的精确 basename，不允许路径段；同名出现零次、超过一次或值冲突都拒绝。
5. GitHub asset API digest 只接受同一 asset id 上格式严格为 `sha256:<64hex>` 的值。
6. 两种来源都存在时必须一致；只有一种时可单独使用；都不存在时不可安装。
7. 下载后的资产 hash 必须与选定校验值常量时间比较。

该信任模型验证传输完整性和 Release 资产一致性，不声称抵御 GitHub 或上游发布账号整体失陷。资产缺失、资产名歧义或校验条件失败时，Release 仍可选中查看详情，但“安装并切换”禁用并显示原因。

插件不从 source archive 编译 RTK，不要求用户安装 Rust，也不以未验证下载满足“全部 Release”。

### 5.3 版本标签

1. stable 与 prerelease 只影响 UI 标签和确认文案，不影响是否进入目录或测试强度。
2. 比活动 Release 更早的 `published_at` 标记为“历史版本切换”，允许选择但要求二次确认。
3. prerelease 标记为“预发布”，允许选择但要求二次确认。
4. 当前活动 Release 禁用“切换”操作，可提供“重新运行兼容性测试”。
5. 已安装非活动版本标记为“已安装”，切换时仍重新运行完整兼容性测试，不能信任旧报告替代当前环境验证。
6. `<binary> --version` 与 tag 比较时仅规范化已知前缀 `v`、`dev-` 和 CLI 固定 `rtk `；其余字符必须一致，不进行宽松数字猜测。

## 6. 初始安装与候选下载

首次安装固定使用已验证基线 `v0.45.0`；在线选择使用 Release id 指定的目标。

统一安全管线：

1. 重新读取目标 Release，校验 release id、tag、asset id 与 UI 看到的 catalog revision。
2. 只接受 GitHub 官方 HTTPS URL，限制重定向次数、总时间和最大字节数。
3. 下载到事务临时目录，流式计算 SHA-256，并与 checksum/digest 常量时间比较。
4. 解压时拒绝绝对路径、`..`、符号链接、硬链接和重复覆盖条目。
5. Unix 设置可执行权限，Windows 使用 `rtk.exe`。
6. 执行版本探测并严格匹配规范化 tag。
7. 版本级锁防止重复安装，事务锁防止并行激活。
8. 候选 side-by-side 安装，绝不覆盖活动目录或数据段。
9. 失败时清理候选临时目录、保留活动版本并写入结构化报告。

配置外部 `binaryPath` 时 Release 目录可只读查看，但安装、切换和回滚操作禁用，因为二进制所有权属于外部配置。

## 7. 更新状态机

```text
idle
  -> catalog-loading
  -> catalog-ready | catalog-failed
  -> candidate-selected
  -> downloading
  -> verifying
  -> testing
  -> activating
  -> ready | update-failed | rolled-back
```

1. Release 行的 `available` 只表示可以进入候选流程，不表示已通过兼容性测试。
2. 下载和校验成功后必须运行第 8 节完整测试。
3. 测试报告先持久化，再进入激活阶段。
4. 激活时 executor 继续使用旧活动快照；新候选先通过 Runtime 公共解析路径冒烟。
5. 冒烟成功后原子更新 `runtime.json` 和内存活动描述符，新命令才读取新版本。
6. 冒烟失败恢复旧描述符并标记 `rolled-back`。
7. 已启动命令始终使用启动时捕获的 binary、PATH 和 RTK_DB_PATH，不在中途换版本。
8. 进程在下载、验证或测试中退出时，下次启动使用旧版本并清理未确认候选。
9. 同一 Release 重复点击返回同一 transaction id；不同候选在事务未结束前拒绝并行激活。

## 8. 强制 RTK 兼容性测试

测试使用隔离临时目录、私有 HOME、临时 `RTK_DB_PATH`、`RTK_TELEMETRY_DISABLED=1`、`shell: false` 和明确 argv。

| 检查               | 通过条件                                                                                                  |
| ------------------ | --------------------------------------------------------------------------------------------------------- |
| `version`          | CLI 版本与规范化 Release tag 一致                                                                         |
| `rewrite-simple`   | `git status` 退出 `0/3` 且 stdout 合法非空                                                                |
| `rewrite-compound` | 复合、多行和已有 RTK fixture 符合退出协议                                                                 |
| `test-pass`        | `rtk test <node> <通过 fixture>` 退出 0                                                                   |
| `test-fail`        | 失败 fixture 返回预期非零和受控摘要                                                                       |
| `fixture-read`     | UTF-8 fixture 的关键内容可读                                                                              |
| `fixture-grep`     | 返回预期匹配                                                                                              |
| `fixture-ls`       | 返回预期目录项                                                                                            |
| `fixture-seed`     | 在 fixture 仓库内外执行已知可跟踪命令，确认临时 DB 产生确定的最少记录                                     |
| `gain-global`      | global JSON 通过 strict schema，`total_commands` 不小于种子数，且 input >= output、saved = input - output |
| `gain-project`     | project JSON 通过 schema，只包含仓库内种子记录并排除仓库外记录                                            |

`fixture-seed` 至少生成仓库内两条和仓库外一条可跟踪记录；后续 gain 断言以这些最小值和范围关系为准，不依赖不同 RTK 版本可能变化的精确 Token 数。

每项 5 秒，整套 45 秒。报告记录 Release id/tag、asset id、SHA-256、每项状态、耗时、退出码和最多 4 KiB 脱敏 stderr 尾部。

任一检查失败、超时、取消或 schema 不兼容都禁止激活。目录中的旧版本若不具备当前插件所需命令，会自然在测试阶段失败；UI 必须显示具体失败项，不能把它隐藏为 stable/prerelease 策略。

## 9. 版本化数据与回滚

```text
$DSH_HOME/plugins/dsh-plugin-rtk/
  bin/<release-id>/<platform-arch>/rtk[.exe]
  data/segments/<release-id>/history.db
  state/runtime.json
  state/installation.json
  state/update-report.json
  state/catalog-cache.json
  tmp/update-<transaction-id>/
  install.lock
  update.lock
```

使用 release id 而不是 tag 作为目录键，防止异常 tag 字符和 tag 重用导致路径冲突。

1. 每个活动 Release 只写自己的 data segment。
2. 每个历史 segment 只由同 Release 保留 binary 执行 gain 读取。
3. 回滚只切换活动描述符，不改写、合并或删除历史 SQLite。
4. 全局/今日/仓库汇总对各 Release JSON 求和并重算比率，细节见 `数据与界面.md`。
5. 历史段不可读时返回 `partial` 和 `unreadableReleases`，不静默当零。
6. 首版不提供删除历史版本的产品 UI。
7. `RTK_TELEMETRY_DISABLED=1` 始终启用，不写用户全局 RTK 配置。

## 10. rewrite 接管

每个非空 shell command 作为一个 argv 传给：

```text
<active-rtk> rewrite <完整原始命令>
```

同步分类唯一例外：

```text
spawnSync(<绝对 RTK 路径>, ['rewrite', <原始命令>], {
  shell: false,
  timeout: 500ms,
  maxBuffer: 1MiB,
  windowsHide: true
})
```

退出协议：

| code           | 行为                                                      |
| -------------- | --------------------------------------------------------- |
| 0              | 使用非空合法 rewrite，仍由 DSH 判权                       |
| 1              | 原样执行，记录 `no-rewrite`                               |
| 2              | 忽略外部权限结论，原样执行并记录 `permission-passthrough` |
| 3              | 使用 rewrite，仍由 DSH 判权                               |
| 其他/超时/异常 | 原样执行，记 technical fallback                           |

stdout 必须是非空 UTF-8、无 NUL 且不超过上限。分类器只解析字符串，不执行目标命令；实际命令仍由 DSH sandbox executor 执行。

命中时一次性读取活动描述符快照，并从同一快照设置 binary PATH 和 `RTK_DB_PATH`。Windows 大小写不敏感合并 Path/PATH。任何失败都保留原命令字节，不改变 DSH approval、workdir、timeout、background、退出码或 sandbox 行为。

## 11. 未命中诊断

`RtkDiagnosticsService` 使用 storage-domain 保存脱敏聚合：

```ts
interface RtkRewriteDiagnostic {
  digest: string
  displayCommand: string
  reason: 'no-rewrite' | 'permission-passthrough'
  releaseId: number
  rtkTag: string
  repositoryRoot: string | null
  shell: 'bash' | 'pwsh'
  count: number
  firstSeenAt: number
  lastSeenAt: number
}
```

1. 写入前脱敏 API key、Token、Authorization、URL 凭据和常见 secret 环境值。
2. 命令按 Unicode 边界截断到 1000 字符，换行以可读转义保存。
3. digest 基于脱敏命令、Release、仓库和原因；切换版本前后分别聚合。
4. 最多保留最近 1000 个不同项，超限淘汰最旧项。
5. hit/miss/technical 按日期、Release 和仓库聚合。
6. 不保存命令输出、环境对象、文件内容或模型消息，不上传数据。
