## 2. 拆分 stop gate

### 2.1 Stage 1H：Host 强制判定闭环

在 RTK 业务编码前，分别在 DSH rc.7 与 rc.1 的隔离 Profile 证明：

1. Standalone package 的 Host entry 可通过公开构建与 `dsh.bundle` patch 安装、启动、停止、重载和移除。
2. 两版本完整内置 shell identity 均为 `bash`、`pwsh`，必填路径均为 `exec.arguments.command: string`；persistent 实现复用相同 identity/schema。
3. Stage 1H 以 test-owned fake rewrite executable 和 ephemeral lease 提供 0/1/2/3 exit、输出、超时及取消矩阵；它不创建生产 Runtime、wrapper 或 active pointer。
4. `RtkCommandGate` 的 async `tools/pre-execute` classifier、execution-token receipt、同步 `ctx.tools.guard()`、`shellEnv` 和 guidance 都归插件 fiber 并可释放。
5. Classifier 使用 `{ prepend:true }`；`next()` 只恢复同一 pre-execute waterfall，不会 dispatch。目标 scheduler 的固定顺序是 waterfall → 必要时 ask approval → synchronous guards → `tools/execute`/body。
6. Guard 是官方 terminal monotonic policy：仅返回 denial reason，另一 listener/guard 不能 force allow；listener throw、deny、ask rejection 或 guard throw 都不得进入 dispatch。Missing receipt 可能在其他 listener 的 ask 后才被 guard 拒绝，但绝不能到达 body/process creation。
7. 真实 rc.7/rc.1 side-effect probe 覆盖前后注册、`next()`、throw、ask、second guard 与 short-circuit；证明 classifier deny 或 guard deny 后无 `tools/execute`、executor/process 和副作用。
8. Gate 不修改 ToolExecution、command、identity 或 signal；无 active lease 时完全放行，active lease 下协议错误和生命周期竞争严格拒绝。

1H 无法证明完整 identity/schema、listener reachability、guard monotonicity、deny short-circuit 或任一目标版本时，记录独立 Host blocker并停止阶段 2 至阶段 5；Client/Typert artifact 不是 1H 前置条件。

### 2.2 Stage 1C：Client/Remote/Slot 闭环

第五版在 2026-08-21 已确认：

1. rc.7/rc.1 的公开 `typertPlugin({ faces: ['host'] })` 在 workspace 根 package 探针中均生成 0 个 artifact。
2. 发布实现和 tagged tests 只发现 aggregate project references 下 `<root>/packages/**` contributor；这是失败诊断，不是公共契约。
3. Client modules 能加载预构建 bundle，但目标版本没有文档化、可导出的第三方 lazy-CJS Client builder。
4. 直接编排 generator、复制 monorepo helper、假 workspace、手写 codec 或 patch runtime 继续禁止。

该结论保持 `blocked-official-api`，只阻断 Remote、Client、Slot、浏览器验收和正式发布。上游提供官方 standalone Typert/Client build path 后，仍须验证 Host artifact、Remote contribution、codec、loader、Client→Host probe、`shell.overlay` 和双端 disposer。

## 3. 架构硬边界

1. 不修改 DSH 源码/安装目录、全局或既有 RTK 安装和运行时对象；只写插件 owner-marked side-by-side segment。
2. 不使用反射、原型枚举、私有字段、深层未导出路径或 monkeypatch。
3. 不替换 DSH Bash/Pwsh executor，不注册第二个 `ctx.shell` 或 shell Tool。
4. Async `tools/pre-execute` classifier 只调用活动 RTK 并生成 execution-token 临时 receipt；同步 `ctx.tools.guard()` 只消费 receipt 并单调拒绝，不改变 command、arguments、approval identity 或 signal。
5. 不在 around-dispatch 或 shell resolve 中改写命令，不复制 RTK rewrite registry、解析 shell grammar 或按前缀豁免“看似已包装”的调用。
6. 不绕过 approval、sandbox、workdir、timeout、background、exit code 和进程生命周期。
7. 不执行全局 `rtk init`、不修改 PATH/profile、不持久化命令文本或 rewrite 建议。
8. 不手写 Typert artifact/codec，不建立兼容 fallback。
9. 不直接读取、查询或迁移 RTK SQLite。

## 4. 总体结构

```text
DSH Profile
  |
  +-- Host Cordis plugin
  |     +-- RtkService（唯一业务 Service）
  |     |     +-- active Runtime 与已安装 Release segments
  |     |     +-- Release 目录、候选测试、安装与切换
  |     |     +-- 跨可读 segments 的 gain 聚合
  |     +-- RtkCommandGate
  |     |     +-- async pre-execute classifier + token receipt
  |     |     +-- active binary: rtk rewrite <command argv>
  |     |     +-- monotonic guard: missing/stale receipt => deny
  |     +-- shellEnv: DSH_RTK_WRAPPER / DSH_RTK_VERSION
  |     +-- agent/session-start guidance v3
  |     +-- rtkDashboard Typert Remote（Stage 1C 后）
  |
  +-- DSH 原 Bash/Pwsh tool + 原 shell executor
  |     +-- Agent 新提交的 wrapper-shaped 命令
  |     +-- 原 approval / sandbox / timeout / background
  |
  +-- Client（Stage 1C 后）
        +-- shell.overlay 悬浮球
        +-- 总览 / 今日 / 当前仓库
        +-- 全 Release 选择器
```

只有 `RtkService` 是 Cordis 业务 Service。`RtkCommandGate` 是 fiber-owned policy adapter，只持有以 execution token 为键、由 guard 原子消费且有 expiry/result/disposer 清理的瞬时 receipt；它不拥有 Runtime、Release 或命令历史。Release、checksum、archive、gain 和 wrapper helper 仍是内部高内聚模块。

## 5. 强制 RTK 判定与直接调用

### 5.1 shellEnv

插件通过官方 `ctx.shellEnv.register()` 提供：

```text
DSH_RTK_WRAPPER = 当前活动 Release 的 wrapper 绝对路径
DSH_RTK_VERSION = 当前活动 Release tag
```

变量和 resolver 归当前 Cordis fiber；卸载后自动消失。不得贡献 PATH、覆盖 DSH 内置变量或修改进程全局环境。

### 5.2 wrapper

每个已安装 Release 有独立 binary、wrapper 和 data 目录。wrapper 只做：

1. 设置该 Release 的 `RTK_DB_PATH`。
2. 设置 `RTK_TELEMETRY_DISABLED=1`。
3. 以原参数启动官方 RTK binary，并原样返回 stdout、stderr 和 exit code。

wrapper 不解析 shell 字符串、不维护命令白名单，也不修改参数。Gate 以绝对 `binaryPath`、`['rewrite', command]` 和该 segment 的显式环境直接 spawn，固定 `shell:false` 且不经 PATH；wrapper 只供最终 DSH shell 调用，gain 可复用 wrapper 或等价的 binary+env helper。

```text
Bash: "$DSH_RTK_WRAPPER" git status
Pwsh: & $env:DSH_RTK_WRAPPER git status
```

DSH 在 pre-policy 前已记录 Agent 提交的参数。Gate 不回显原 command、raw stdout/stderr 或 RTK suggestion，只返回不超过 1 KiB 的稳定 code 与 Bash/Pwsh wrapper 模板；Agent 根据自己刚提交的调用构造新的 ToolExecution，wrapper、子命令和参数再次完整进入内置判权和 sandbox。RTK 输出是 shell program 而非 authorization/argv；插件不得机械前缀化或自动执行它。compound command 无法由 Agent 安全构造时返回 `manual-retry-required` 并保持拒绝，不猜 shell 语义，也不承诺任意 shell program 都能成功收敛。

`DSH_RTK_WRAPPER` 是可被 shell command shadow 的 guidance binding，不是授权或执行身份证明。Gate 只保证新的 wrapper-shaped ToolExecution 被再次分类/判权，不能声称它最终一定调用 verified active wrapper；是否实际产生 RTK gain 以 RTK 自有统计为准。

Agent-visible reason code allowlist 固定为 `RTK_REWRITE_REQUIRED`、`RTK_MANUAL_RETRY_REQUIRED`、`RTK_POLICY_DENIED`、`RTK_CLASSIFICATION_FAILED`、`RTK_RECEIPT_MISSING` 和 `RTK_RUNTIME_CHANGED`；reason 只含 code、tool、platform、retryKind 和通用 env-var 模板。

### 5.3 RtkCommandGate

```text
受覆盖 ToolExecution（name=bash|pwsh，冻结 arguments）
  -> async classifier（prepend）
       -> 先写 pending provenance { token, startedMode, generation? }
       -> startedMode=inactive：转为 inactive-start receipt，再调用 next()
       -> schema 错误：deny(RTK_TOOL_SCHEMA_MISMATCH)
       -> 捕获 lease { generation, binaryPath, wrapperPath, assetDigest, contract }
       -> spawn binaryPath ['rewrite', command]，解析候选专属 contract
       -> allow 结论：写入 enforcing receipt，再调用 next()
       -> exit-3-same：写 receipt，组合 downstream deny，否则返回 ask
       -> rewrite / policy / failure 结论：直接 deny，不执行 suggestion
  -> DSH 全部 pre-execute listener 完成
  -> monotonic guard（先读取并删除 receipt，再判断当前 mode）
       -> inactive receipt + 当前 inactive：allow
       -> enforcing receipt + 当前 enforcing 且同 generation：allow
       -> receipt/current mode 不匹配、generation 漂移或重复消费：deny
       -> 无 receipt + 当前 enforcing/draining/tombstone：deny
       -> 无 receipt + 当前 inactive：allow
  -> final allow 才进入 tools/execute / sandbox / executor（ask approval 已按 scheduler 顺序在 guard 前处理）
```

目标 RTK `v0.44.2`/`v0.45.0` tagged source 只是诊断基线；每个 candidate 必须以真实 binary、CLI help 和 tagged contract evidence 固化以下穷尽矩阵，未列组合全部 deny：

| Exit | stdout               | stderr               | RTK 语义             | DSH decision                  |
| ---- | -------------------- | -------------------- | -------------------- | ----------------------------- |
| `0`  | valid、与 input 不同 | candidate 证明可接受 | Allow rewrite        | deny + generic retry template |
| `0`  | valid、与 input 相同 | candidate 证明可接受 | converged            | allow                         |
| `1`  | empty                | candidate 证明可接受 | Passthrough          | allow                         |
| `2`  | empty                | candidate 证明可接受 | RTK policy deny      | deny                          |
| `3`  | valid、与 input 不同 | candidate 证明可接受 | Ask rewrite          | deny + generic retry template |
| `3`  | valid、与 input 相同 | candidate 证明可接受 | Ask on final command | ask，交给 DSH approval        |

Exit `3` empty 永远无效；同字节不能把 Ask 降成 allow。协议归一化只允许删除一个末尾 LF 或 CRLF；其余 CR/LF、NUL、无效 UTF-8、exit/output 组合漂移均拒绝，禁止 broad trim。Candidate contract 还必须明确每个合法行是否允许 nonempty stderr；未明确或越过 64 KiB 即 deny，stderr 永不回显。

Gate 不修改 `exec`，不自行执行目标命令，也不把 rewrite 当授权。Subprocess 固定 `shell:false`、绝对 binary path、单个 command argv、`RTK_TELEMETRY_DISABLED=1`、2 秒硬超时、stdout/stderr 各 64 KiB；stderr 只限流并丢弃。转发 `exec.signal`：取消或 disposer 先发生时立即 deny，终止 child、最多等待 1 秒 reap、移除 listener 并忽略迟到输出。

Receipt key 必须是 rc.7/rc.1 公开、registry-issued 且同一调用内共享的唯一 `exec.token` symbol，不得由插件生成或复用。One-shot state 为 `pending(startedMode,generation?) | inactive-start | enforcing-classified(generation, contractId, allow|ask) | consumed`，不含 command/output；Map 原子 `get+delete`，missing/mismatch/expired 都 deny。Classifier direct-deny、spawn/cancel error 或 `next()` throw 都先删除；guard consume 是 allow 正确性 Owner；`tools/result`、10 分钟 TTL 和 fiber disposer 只做幂等泄漏清理，不能授权，process restart 后 Map 为空。适用性语义由 verified active binary 提供，DSH gate 只保证 covered ToolExecution 被分类或拒绝。每次 Agent retry 都是新的 ToolExecution，不自动重试或设“已包装”字符串旁路。

`inactive` 与 `enforcing` 是仅有的外部 Runtime mode。保证边界以 guard decision 为准：activation commit 前已通过 inactive guard 的调用不被追溯拦截；inactive-start receipt 在 activation 已 commit、尚未过 guard 时因 mode 不匹配而拒绝。Active pointer 存在即 enforcing；单次失败只返回 denial，不持久化 `blocked`。

Runtime 不提供“插件继续挂载但清空 active pointer”的操作。Switch 只做 active generation 原子替换，旧 receipt 拒绝。Stop/unload 先以 exclusive lifecycle latch 进入内部 `draining`，禁止 classifier 再发布 receipt，保留 enforcing pointer/tombstone、listener 和 guard，取消 child，并等待 pending token 穿过 guard/result。只有真实 rc.7/rc.1 证明 pipeline quiescence 后才能原子移除 gate 与 pointer；否则 Stage 1H 阻断。Guard 始终先看 start provenance：active-start receipt 在 pointer 消失/变化时 deny，missing receipt 在 draining/tombstone 下 deny。

## 6. Runtime 与数据段

```ts
interface RtkInstalledSegment {
  releaseId: number
  tagName: string
  reportedVersion: string
  supportTier: 'guaranteed' | 'best-effort'
  binaryPath: string
  wrapperPath: string
  dataPath: string
  assetId: number
  assetDigest: string
  testedAt: number
}

interface RtkActivePointer {
  releaseId: number
  generation: number
  assetDigest: string
  rewriteContractId: string
  activatedAt: number
}
```

状态要求：

1. active pointer 是活动版本唯一真相，只引用通过完整 rewrite contract 的 segment；generation 在 activate、stop 和 unload 时单调递增且不复用。
2. `rewriteContractId` 是 plugin contract version、asset digest、CLI-help digest 与 canonical exit/stdout/stderr matrix 的 SHA-256；Gate 捕获不可变 lease `{ generation, releaseId, binaryPath, wrapperPath, assetDigest, rewriteContractId }`，guard 必须同时比较 generation 和 contract id。
3. binary、wrapper、data 都在同一 Release 目录；激活校验 checksum、CLI contract、路径存在性与 wrapper probe，运行期缺失/指针损坏严格拒绝。
4. 候选 side-by-side 创建，不覆盖活动 segment；激活只原子替换 active pointer，失败保留旧 pointer。
5. Client、guidance 和 executor 不维护旁路 tag/path；历史 segment 不因切换删除，并由对应 binary 读取自己的 gain JSON。
6. 聚合只包含实际安装且 schema 可读的 segment；不可读段进入 partial 报告。
7. 本产品信任边界是本地已校验官方 asset 与任务拥有的安装目录；command 作为 subprocess argv 临时传给该 binary，可能被操作系统诊断观察，但插件不记录、不回显、不发送 UI/Remote。

## 7. Release 目录与支持等级

目录来自 GitHub 官方 `rtk-ai/rtk` Releases API：

1. 分页读取所有 `draft:false` Release。
2. stable、prerelease 和历史版本全部可见、可选和查看详情。
3. tag 是目录 identity；排序使用 `published_at` 和 release id。
4. 所有行都可发起能力预检；缺本平台官方资产或可信 checksum/digest 时显示原因并阻止下载/激活。
5. 资产选择使用明确平台映射，不从未知文件名猜架构。
6. GitHub asset digest 与 `checksums.txt` 并存时必须一致。
7. 下载限制到 GitHub 官方 API、Release asset 和受信 redirect host。
8. 归档拒绝绝对路径、`..`、链接、重复目标、设备文件和越界大小。

支持等级由候选 binary 的 `--version` 决定：

- `>=0.44.2`：`guaranteed`，属于持续回归和缺陷修复范围。
- `<0.44.2` 或无法解析标准版本：`best-effort`，明确标注“不受保证”，不增加专用兼容分支。

两类候选都执行同一强制测试，但测试 fixture 不能单独创造 contract。只有 asset 可绑定官方 tag/source/CLI evidence，且真实 binary matrix 一致时才能 enforcing；`<0.44.2` 满足该证据仍可作为 best-effort 激活。版本不可解析、tag/asset 无法绑定或 contract 无官方证据时只能浏览、下载并保留为 inactive inspection，不从目录隐藏。

## 8. 候选兼容性测试

候选激活前顺序执行：

1. Binary `--version` 成功，记录版本、asset digest、support tier、CLI help 和 rewrite contract id；任何候选都不得以 best-effort 跳过 contract。
2. 真实 binary 固化 exit `0/1/2/3`、stdout/stderr、严格 UTF-8、末尾换行和 same-input 矩阵；其他 exit、malformed、oversized、timeout 全部得到 deny。
3. Wrapper 在含空格/非 ASCII 的路径使用候选 binary/data 并禁用遥测；Host classifier 直接 spawn 绝对 binary path，Windows 也不经 shell/PATH。
4. `bash`/`pwsh`、registry-issued token、missing/wrong-type/empty command、unknown non-target Tool、inactive-start、缺/过期 receipt、duplicate listener 和 short-circuit 都有明确 pass/fail assertion。
5. 真实 scheduler fixture 证明 classifier `next()` 只进入 listener chain；raw applicable/schema failure 直接 deny 且不触发 approval，missing/stale receipt 即使经过 ask 也在 `tools/execute`/process 前拒绝，无 raw side effect。
6. Retry 矩阵覆盖 exit-0-same/no-match 的可执行路径、exit-3-same 的 DSH ask、再次 rewrite、重复 deny、`manual-retry-required`、literal `rtk` 无 PATH、env shadow 与 Bash/Pwsh 模板；不宣称任意程序都收敛或实际 wrapper identity 已验证。
7. Shell fixture 覆盖 pipe、`&&`、redirect、heredoc、alias、env prefix、substitution 与 PowerShell pipeline；RTK unsupported/no-match 可执行，适用 raw 不执行，插件从不自行解析或猜写。
8. 取消/生命周期覆盖 spawn 前、运行中、stdout 后 exit 前、activation/switch、classifier allow 后 downstream pending、drain/pointer clear/reload 和 dispose；child 1 秒内 reap，迟到输出无效。
9. Receipt fixture 覆盖 downstream/guard throw、approval cancel、abandoned result、atomic consume、expiry、result/disposer 清理、concurrency 和 process restart，证明 stale token 永不授权且无泄漏。
10. 含 token/password/credential URL 的 fixture 证明 denial、日志投影、Remote/UI 不回显 command、stdout/stderr、suggestion、路径或环境值。
11. 在任务拥有的 Git/文本 fixture 执行官方 direct filter，并验证两种 gain JSON；所有 subprocess 和输出边界有界收束。

测试不调用 `rtk init`，不读取用户默认 DB，不修改 shell 配置。任何一项失败都不得激活；旧 Runtime 继续服务。guaranteed 候选失败还会阻断当前阶段完成。

## 9. 会话指导

监听官方 `agent/session-start`：

| source    | 行为                           |
| --------- | ------------------------------ |
| `startup` | 有活动 wrapper 时注入          |
| `clear`   | 新上下文重新注入               |
| `compact` | 压缩后重新注入                 |
| `resume`  | 缺少同版本 typed source 时补入 |

使用 typed source `kind:rtk-guidance`、`version:3` 和 active release identity，不按文案猜测去重。切换 active Release 后旧 tag 不阻止新 source 注入。

```text
RTK 强制判定已启用，当前版本为 <tag>。对于 RTK 支持且不会改变语义的 Bash/Pwsh 命令，优先通过 "$DSH_RTK_WRAPPER" <子命令和参数> 或 & $env:DSH_RTK_WRAPPER <子命令和参数> 执行，以减少首次拒绝并返回更少 Token。直接提交的适用原命令会被拒绝并返回稳定 wrapper 模板；请提交新的调用。compound command 只在能保持每个 RTK segment 语义时构造，否则停止重试。最终命令仍由 DSH 判权和 sandbox 执行；不要覆盖 `DSH_RTK_WRAPPER`、自动执行建议、重复有副作用的命令或绕过权限。
```

## 10. 资源与失败语义

1. Host 下载、文件和 subprocess 使用公开 Node/DSH API，并接受 `AbortSignal`。
2. timer、event、shellEnv、command gate、Remote 和 Slot 均归当前 Cordis fiber。
3. 每次判定新建短生命周期 rewrite subprocess；不建立后台 daemon，不保持 RTK 常驻进程。
4. 临时目录带 owner marker，只删除本事务创建的路径。
5. 网络、校验、测试、激活、rewrite 和 gain 错误投影稳定 code，不发送 Error、stack、绝对路径或原命令全文。
6. 单段 gain 失败不影响 wrapper；聚合标记 partial/unreadable。
7. Rewrite 失败只阻断当前 shell 调用，不自动切换 active pointer；用户停止/卸载插件后原 shell 恢复。
