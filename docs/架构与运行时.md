版本规则：

1. DSH 最低兼容 `0.1.0-rc.7`；npm 已发布的 `0.1.1-rc.1` 同时进入验证矩阵。
2. `master` 文档可能领先发布包；编码 API 必须由对应版本 exports、`.d.ts` 和官方文档共同证明。
3. RTK `develop` 文档可能领先候选 binary；每个候选必须通过自己的 CLI 兼容性测试。
4. 查看源码只辅助理解；生产实现不得复制、修改、镜像或依赖源码目录结构。

## 2. 阶段 1 双端 stop gate

在 RTK 业务编码前，使用最小 `probe(): { ok: true }` 验证：

1. 外部独立 package 可通过官方工具构建 Host 和 Client entry。
2. 官方 Typert 流程可从本仓库生成 Host artifact、Remote contribution 和 codec。
3. `dsh.client`、`./typert`、`./remote` 和 Client bundle 可被官方 loader 发现。
4. Client 可调用 Host probe，并在 `shell.overlay` 注册和卸载一个最小 entry。
5. startup、stop、reload 和 disposer 在隔离 Profile 中生效。
6. 上述闭环在 DSH rc.7 和 rc.1 都通过。

不得复制 DSH 源码、镜像协议声明、构造假 workspace、手写 codec 或 patch runtime。任一项失败即记录 `blocked-official-api`，暂停整个项目；不发布 Host-only 版本。

## 3. 架构硬边界

1. 不修改 DSH 或 RTK 源码、安装目录和运行时对象。
2. 不使用反射、原型枚举、私有字段、深层未导出路径或 monkeypatch。
3. 不替换 DSH Bash/Pwsh executor，不注册第二个 `ctx.shell`。
4. 不在工具 pre-policy、around-dispatch 或 shell resolve 中改变 command。
5. 不绕过 approval、sandbox、workdir、timeout、background、exit code 和进程生命周期。
6. 不手写 Typert artifact/codec，不建立兼容 fallback。
7. 不直接读取、查询或迁移 RTK SQLite。

## 4. 总体结构

```text
DSH Profile
  |
  +-- Host Cordis plugin
  |     +-- RtkService（唯一业务 Service）
  |     |     +-- 活动描述符与已安装 Release segments
  |     |     +-- Release 目录、候选测试、安装与切换
  |     |     +-- 跨可读 segments 的 gain 聚合
  |     +-- shellEnv: DSH_RTK_WRAPPER / DSH_RTK_VERSION
  |     +-- agent/session-start guidance
  |     +-- rtkDashboard Typert Remote
  |
  +-- DSH 原 Bash/Pwsh tool + 原 shell executor
  |     +-- Agent 提交的最终 wrapper 命令
  |     +-- 原 approval / sandbox / timeout / background
  |
  +-- Client
        +-- shell.overlay 悬浮球
        +-- 总览 / 今日 / 当前仓库
        +-- 全 Release 选择器
```

只有 `RtkService` 是 Cordis 业务 Service。Release、checksum、archive、gain 和 wrapper helper 是内部高内聚模块，不各自注册 Service。

## 5. 直接 RTK 调用

### 5.1 shellEnv

插件通过官方 `ctx.shellEnv.register()` 提供：

```text
DSH_RTK_WRAPPER = 当前活动 Release 的 wrapper 绝对路径
DSH_RTK_VERSION = 当前活动 Release tag
```

变量和 resolver 归当前 Cordis fiber；卸载后自动消失。不得贡献 PATH、覆盖 DSH 内置变量或修改进程全局环境。

### 5.2 wrapper

每个已安装 Release 有独立 binary、wrapper 和 data 目录。wrapper 只做：

1. 设置该 Release 的 `RTK_DB_PATH`。
2. 设置 `RTK_TELEMETRY_DISABLED=1`。
3. 以原参数启动官方 RTK binary，并原样返回 stdout、stderr 和 exit code。

wrapper 不调用 `rtk rewrite`，不解析 shell 字符串，不维护命令白名单，也不修改参数。

```text
Bash: "$DSH_RTK_WRAPPER" git status
Pwsh: & $env:DSH_RTK_WRAPPER git status
```

DSH 在 pre-policy 前已看到 wrapper、子命令和参数，随后走内置工具的完整判权和 sandbox 流程。没有活动 wrapper 时不注入指导，原 shell 保持可用。

## 6. Runtime 与数据段

```ts
interface RtkInstalledSegment {
  releaseId: number
  tagName: string
  reportedVersion: string
  supportTier: 'guaranteed' | 'best-effort'
  binaryPath: string
  wrapperPath: string
  dataPath: string
  assetId: number
  assetDigest: string
  testedAt: number
}

interface RtkActivePointer {
  releaseId: number
  activatedAt: number
}
```

状态要求：

1. active pointer 是活动版本唯一真相，引用一个已验证 segment。
2. binary、wrapper、data 都在同一 Release 目录。
3. 候选 side-by-side 创建，不覆盖活动 segment。
4. 激活只原子替换 active pointer；失败保留旧 pointer。
5. Client、guidance 和 executor 不维护旁路 tag/path。
6. 历史 segment 不因切换删除，并由对应 binary 读取自己的 gain JSON。
7. 聚合只包含实际安装且 schema 可读的 segment；不可读段进入 partial 报告。

## 7. Release 目录与支持等级

目录来自 GitHub 官方 `rtk-ai/rtk` Releases API：

1. 分页读取所有 `draft:false` Release。
2. stable、prerelease 和历史版本全部可见、可选和查看详情。
3. tag 是目录 identity；排序使用 `published_at` 和 release id。
4. 所有行都可发起能力预检；缺本平台官方资产或可信 checksum/digest 时显示原因并阻止下载/激活。
5. 资产选择使用明确平台映射，不从未知文件名猜架构。
6. GitHub asset digest 与 `checksums.txt` 并存时必须一致。
7. 下载限制到 GitHub 官方 API、Release asset 和受信 redirect host。
8. 归档拒绝绝对路径、`..`、链接、重复目标、设备文件和越界大小。

支持等级由候选 binary 的 `--version` 决定：

- `>=0.44.2`：`guaranteed`，属于持续回归和缺陷修复范围。
- `<0.44.2` 或无法解析标准版本：`best-effort`，明确标注“不受保证”，不增加专用兼容分支。

两类候选都执行同一强制测试；best-effort 测试成功时可以激活，失败时只阻止该候选，不从目录隐藏。

## 8. 候选兼容性测试

候选激活前顺序执行：

1. binary `--version` 成功，记录 reported version 和 support tier。
2. wrapper 使用候选 binary/data，并禁用遥测。
3. 在任务拥有的 Git fixture 执行官方直接命令，例如 `rtk git status`。
4. 在文本 fixture 执行该版本可用的过滤命令。
5. `gain --all --format json` 返回符合 schema 的 JSON。
6. `gain --project --all --format json` 在 fixture cwd 返回有效 JSON。
7. stdout/stderr、非零退出、超时和取消均有界收束。

测试不调用 `rtk init`，不读取用户默认 DB，不修改 shell 配置。任何一项失败都不得激活；旧 Runtime 继续服务。guaranteed 候选失败还会阻断当前阶段完成。

## 9. 会话指导

监听官方 `agent/session-start`：

| source    | 行为                           |
| --------- | ------------------------------ |
| `startup` | 有活动 wrapper 时注入          |
| `clear`   | 新上下文重新注入               |
| `compact` | 压缩后重新注入                 |
| `resume`  | 缺少同版本 typed source 时补入 |

使用 typed source `kind:rtk-guidance`、`version:2`，不按文案猜测去重。

```text
RTK 已可用。语义等价时，可在 Bash 使用 "$DSH_RTK_WRAPPER" <命令>，在 PowerShell 使用 & $env:DSH_RTK_WRAPPER <命令>，让 RTK 压缩输出。最终命令仍由 DSH 判权和 sandbox 执行；不要为使用 RTK 改变语义或绕过权限。
```

## 10. 资源与失败语义

1. Host 下载、文件和 subprocess 使用公开 Node/DSH API，并接受 `AbortSignal`。
2. timer、event、shellEnv、Remote 和 Slot 均归当前 Cordis fiber。
3. 临时目录带 owner marker，只删除本事务创建的路径。
4. 网络、校验、测试、激活和 gain 错误投影稳定 code，不发送 Error、stack 或绝对路径。
5. 单段 gain 失败不影响 wrapper；聚合标记 partial/unreadable。
6. 不建立后台 daemon，不保持 RTK 常驻进程。
