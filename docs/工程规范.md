# 工程规范

- 状态：第四版计划组成部分，已批准，实施中
- 上级入口：`docs/开发计划.md`
- 唯一职责：项目结构、文件规模、模块边界、质量工具、注释和测试质量

## 1. 工程目标

项目必须是可独立克隆、安装依赖、构建、测试、打包和发布的标准 TypeScript 工程。目录、Owner、依赖方向和质量门禁由仓库配置自动验证，不能只依赖人工约定。

质量原则：

1. 高内聚：一个文件只服务一个 Owner 或一个紧密相关的纯函数集合。
2. 低耦合：跨模块只通过公开类型、port 或 Remote contract 连接。
3. 单一真相：Release 目录、活动版本、rewrite、Token 和 UI 状态各有唯一 Owner。
4. 可替换：网络、文件、子进程、时钟和 GitHub API 通过可注入 port 测试，不在业务逻辑中硬编码。
5. 可收束：所有异步、订阅、timer、进程和临时资源有 Cordis 生命周期或显式 disposer。
6. 可验证：规模、复杂度、依赖图、覆盖率、包内容和跨平台构建进入 CI。

## 3. 单文件规模门禁

### 3.1 硬限制

1. 所有手工维护的 TypeScript、TSX、JavaScript、CSS、JSON、YAML、Markdown、脚本和测试文件最多 400 个物理行。
2. 400 行包含空行和注释；详细中文注释不能作为突破上限的理由。
3. 日常目标为不超过 250 行；超过 250 行时 code review 必须确认文件仍只有一个职责。
4. 达到 350 行时禁止继续追加新职责，必须先按 Owner 或纯 helper 拆分。
5. 达到 400 行直接使 `pnpm run check:lines` 和 CI 失败，不接受 warning-only。

### 3.2 唯一例外

以下机器生成文件可排除 400 行门禁：

- `pnpm-lock.yaml`。
- `lib/`、`dist/` 内构建产物。
- Typert 生成 codec。
- coverage、Playwright、package manager 和编译器生成目录。

例外必须同时满足：生成来源可重现、路径在检查脚本显式 allowlist、文件不手工编辑、源码 Owner 仍在 400 行内。手工 fixture、配置、文档和测试不能伪装成 generated exception。

### 3.3 自动执行

`scripts/check-file-lines.mjs` 从 Git tracked files 和预提交待跟踪文件构建集合，按 UTF-8 换行计数，拒绝：

- 手工文件超过 400 行。
- 未知二进制或不可解码文本进入发布文件列表。
- generated allowlist 中不存在的路径被跳过。
- 标记 generated 的文件没有对应生成命令。

`pnpm run check:lines` 在本地 `check`、prepack 和三平台 CI 中运行。当前五份计划文档也必须通过同一限制。

## 4. 函数与复杂度门禁

生产源码：

| 指标               | 硬限制 |
| ------------------ | ------ |
| 单函数物理行       | 60     |
| 圈复杂度           | 10     |
| 最大嵌套深度       | 4      |
| 参数数量           | 5      |
| 单文件公开导出     | 8      |
| 单模块直接内部依赖 | 8      |

测试 callback 允许最多 100 行，但应优先提取 fixture builder。React component、hook、service method 和 Cordis `apply()` 都受生产 60 行限制。

ESLint flat config 启用 `max-lines`、`max-lines-per-function`、`complexity`、`max-depth`、`max-params` 和 `import/no-cycle`。不得使用 disable comment 永久绕过；确有第三方类型兼容时，例外必须精确到一行并用中文说明原因和删除条件。

## 5. 模块边界

### 5.1 Host 领域

- `runtime`：活动描述符、版本段注册和运行快照。
- `releases`：GitHub 分页、Release schema、平台资产能力。
- `updates`：候选事务、兼容性测试、激活和回滚。
- `guidance`：Session lifecycle 注入。
- `rewrite`：同步分类与退出协议。
- `diagnostics`：脱敏命中/未命中聚合。
- `metrics`：单段 gain schema 与跨段聚合。
- `remote`：Typert 输入输出投影，不写业务规则。
- `executors`：DSH Bash/Pwsh adapter，只消费 runtime/rewrite ports。

### 5.2 Client 领域

- `overlay`：悬浮球、拖动和展开状态。
- `releases`：目录、筛选、确认和更新进度。
- `dashboard`：数据加载、缓存投影和错误状态。
- `tabs`：四个标签页的展示组件。
- `shared`：无业务 Owner 的格式化与可访问性 primitive。

### 5.3 依赖规则

1. Host 与 Client 只能共享 `src/shared` 的 JSON contract/schema，不互相导入实现。
2. executor 不导入 Release HTTP client、UI 或 storage 实现。
3. Update Service 不直接修改 executor；只通过 Runtime port 发布已验证描述符。
4. Remote 不直接读文件、跑进程或计算业务指标；调用对应 service。
5. React component 不直接调用 Host Remote；统一经过 typed hook/controller。
6. tab 之间不互相导入，公共展示逻辑下沉到 client shared。
7. 禁止跨 Owner 深路径导入 `../other-owner/internal-file`；只从 Owner public entry 导入。
8. 禁止循环依赖、双向 service reference、全局 mutable singleton 和模块加载时后台任务。

`.dependency-cruiser.cjs` 验证分层和无环；`pnpm run check:deps` 失败即阻断阶段提交。

## 6. TypeScript 与契约

1. 开启 `strict`、`noUncheckedIndexedAccess`、`exactOptionalPropertyTypes`、`useUnknownInCatchVariables`、`noImplicitOverride` 和 `noFallthroughCasesInSwitch`。
2. 禁止 `any`；外部数据先作为 `unknown`，通过 Zod 或生成 codec 收窄。
3. 对关闭 union 使用 `assertNever`，Release/更新状态不得用任意字符串散落判断。
4. Host/Client Remote 只传 lossless JSON。
5. Error 通过稳定 code、message 和最小 metadata 投影，不传 Error 实例或 stack 给 Client。
6. 时间使用 epoch milliseconds 或明确 ISO-8601；版本身份使用 GitHub release id 和原始 tag。
7. 路径只在 Host 内使用规范化绝对路径；Client 只接收安全显示值。
8. package public API 只从根 exports 暴露 DSH plugin entry，不暴露内部 service class。

## 7. 中文注释规范

1. 文件级：说明职责、Owner、输入输出、生命周期和禁止承担的职责。
2. 函数级：说明参数、返回、失败语义、调用边界和不变式。
3. 关键语句级：解释 Release 筛选、checksum、测试门禁、原子激活、回滚、rewrite 退出码、PATH 合并、脱敏、缓存和拖动阈值等非显然原因。

注释必须回答“为什么”和“失败会怎样”，不逐句翻译语法。明显赋值、简单条件和普通 JSX 不堆叠无信息注释。生成文件保留生成器头，不手工补中文注释。

## 8. 测试与覆盖率

Vitest 全局门禁：

| 指标       | 最低值 |
| ---------- | ------ |
| statements | 85%    |
| lines      | 85%    |
| functions  | 85%    |
| branches   | 80%    |

高风险 Owner `releases`、`updates`、`rewrite`、`executors`、`metrics` 单独要求 statements/lines/functions 95%、branches 90%。覆盖率不能通过排除业务文件、无断言测试或只测 mock 调用满足。

测试层次：

1. pure unit：Release 归一化、资产选择、checksum、状态机、聚合、脱敏和格式化。
2. service unit：使用注入 port 模拟网络、时钟、文件和 subprocess。
3. contract：Typert codec、Zod schema、错误 code 和 catalog cursor。
4. integration：真实基线 RTK、fixture Release server、DSH executor 和 storage lifecycle。
5. browser：Playwright 三档视口、键盘、拖动、Release 目录和四标签页。
6. package：`pnpm pack --dry-run` 和安装后入口验证。

## 9. 重复、未使用与依赖治理

1. `jscpd` 对 `src` 和手工测试执行，复制率上限 3%；fixture 数据不参与文本重复率。
2. `knip` 检查未使用文件、exports 和 dependencies。
3. package dependencies 使用精确或受控范围，运行依赖与开发依赖分离。
4. Dependabot 每周检查 npm 和 GitHub Actions；升级仍需三平台 CI。
5. 禁止把通用 helper 提前做成万能工具包；只有两个以上 Owner 使用且语义一致时才进入 shared。
6. 重复测试数据优先 fixture builder，不复制大块 JSON。

## 10. 格式、提交与发布质量

1. Prettier 统一格式，ESLint 统一静态规则；CI 使用 check 模式，不在验证阶段自动改文件。
2. `.editorconfig` 固定 UTF-8、LF、末尾换行和空白规则；`.gitattributes` 处理脚本与 Windows 包装器。
3. `package.json` 定义 `engines`、`exports`、`files`、`sideEffects`、license、repository、bugs 和 homepage。
4. `README.md`、`README.zh.md`、`CONTRIBUTING.md`、`SECURITY.md`、`CHANGELOG.md` 与 MIT LICENSE 完整。
5. tarball 不包含 RTK 二进制、源码测试输出、coverage、截图、临时数据库或本机路径。
6. 提交精确暂存，主题和正文使用详细中文，列出行为、验证和边界。
7. 每阶段 push 后核对本地/远端 SHA，禁止 force push。

## 11. 统一质量命令

```text
pnpm install --frozen-lockfile
pnpm run format:check
pnpm run lint
pnpm run check:lines
pnpm run check:deps
pnpm run check:unused
pnpm run check:duplication
pnpm run typecheck
pnpm run test:coverage
pnpm run bundle
pnpm run check:package
pnpm pack --dry-run
pnpm run check
```

`pnpm run check` 聚合所有非浏览器门禁，并在三平台 CI 执行。任一门禁失败都不得提交阶段完成、推送后续阶段或创建 Release。
